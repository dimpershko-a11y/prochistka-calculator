# CONTRACT_GENERATOR_SPEC.md — техническое задание генератора договоров

Статус: **5 решений согласованы; 6 исходных DOCX/PDF получены и сверены 14.10.2026**. Карта исходников — [DOCUMENT_TEMPLATE_MAPPING.md](DOCUMENT_TEMPLATE_MAPPING.md). Юридические и налоговые формулировки подлежат отдельной проверке. Production не изменена.

## 1. Задача и границы MVP
Цель: из существующего **сохранённого заказа** открыть редактируемый договор на клининговые услуги, автоматически заполнить поля, перечень работ, приложения и сумму, показать предварительный просмотр и вывести пригодный для печати PDF. Базовое ядро `CORE.calculateOrder` не дублировать. Первая версия: **один редактируемый шаблон, один договор на заказ, PDF, сохранение черновика, индикация расхождения цены**. DOCX, акт и несколько шаблонов — только после стабилизации.

### Опорные существующие функции
- `assets/core.js:calculateOrder` — расчёт текущего заказа;
- `assets/js/main.js` обработчик `saveOrderBtn` — запись `savedOrders`;
- `assets/js/estimate.js:renderSavedOrders/repeatSavedOrder` — существующий интерфейс;
- `assets/js/helpers.js:getIncludedLines` и `state.cleaningTypes[cleanType].included/notIncluded` — описания работ;
- `assets/js/estimate.js:buildPrintHtml/generatePdfBlob` — ориентир стиля/экспорта, **но экспорт договора должен быть многостраничным A4**;
- `assets/js/state.js:saveState` и экспорт backup — хранение и миграция.

## 2. Центральное правило: неизменяемый снимок заказа
Создавать **`quoteSnapshot` один раз в момент сохранения заказа**, чтобы новые тарифы не меняли уже согласованную цену, позиции, описания и условия. У существующих старых заказов брать сохранённое `recommendedPrice`, `form`, `extras`, `calculation`; отсутствующие исторические описания помечать «не сохранено в старом заказе» и требовать подтверждения перед договором. **Не подставлять новые тарифы молча.**

Предлагаемые поля (схематично):
```json
{
  "schemaVersion": 1,
  "orderId": "stable-id",
  "createdAt": "ISO date",
  "appVersion": "v4.11.24",
  "configRevision": 24,
  "client": {"name": "", "phone": "", "email": ""},
  "object": {"address": "", "type": "", "areaM2": 0},
  "service": {"typeKey": "", "label": "", "included": [], "notIncluded": []},
  "schedule": {"date": "", "startTime": "", "estimatedEndTime": ""},
  "items": [{"id": "service-id", "name": "", "unit": "шт", "qty": 1, "unitPrice": 0, "lineTotal": 0, "description": ""}],
  "pricing": {"base": 0, "extras": 0, "travel": 0, "discount": 0, "total": 0, "currency": "RUB"},
  "legalBasis": {"templateId": "", "templateVersion": ""}
}
```
Числа — только конечные значения, единицы измерения и ставки фиксируются как значения на дату согласования. Первичная цена `quoteSnapshot.pricing.total` неизменяема.

## 3. Договор — отдельная редактируемая копия
`contractDraft` не изменяет `savedOrders`/ `quoteSnapshot` автоматически.
```json
{
  "schemaVersion": 1,
  "contractId": "uuid",
  "orderId": "stable-id",
  "sourceQuoteHash": "sha256",
  "templateId": "cleaning-b2c",
  "templateVersion": 1,
  "documentNo": "",
  "documentDate": "",
  "parties": {"customer": {}, "contractor": {}},
  "schedule": {"startTime": "", "endTime": ""},
  "editedItems": [],
  "extraConditions": "",
  "textOverrides": {},
  "priceOverrideReason": "",
  "status": "draft",
  "updatedAt": "ISO date"
}
```
Отдельно хранить флаги полей: `source='order'|'manual'`, дату изменения, исходное и текущее значение; показывать отличия в UI. Удаление работы из договора не удаляет её из заказа. Перечень работ автоматически подставлять только из выбранного вида уборки и реально выбранных допуслуг; особое правило по окнам — подключать окно-описание только когда есть выбранная оконная услуга.

## 4. Источники полей и отсутствие повторного ввода
| Поле | Откуда брать | Поведение |
|---|---|---|
| Заказчик/телефон | `savedOrder.form.clientName/clientPhone` | Правка только в черновике |
| Адрес/тип/площадь | `savedOrder.form` | Перенос из снимка |
| Дата уборки | `savedOrder.form.cleanDate` | Правка в договоре |
| Время начала/конца | Новые поля черновика | Нет в основной форме — не выдумывать |
| Тип/описание уборки | `quoteSnapshot.service` | Фиксированный текст на дату |
| Допуслуги и объём | `quoteSnapshot.items` | Только выбранные; цены фиксируются |
| Стоимость | `quoteSnapshot.pricing.total` | Красное предупреждение при изменении |
| Компания и контакты | Настройки компании | Юридические реквизиты отдельным блоком |
| Номер/дата договора | Генератор | Номер можно исправить вручную |

## 5. Правила ценовой согласованности
1. Начальная стоимость договора = `quoteSnapshot.pricing.total`.
2. При редактировании количества/цены одной позиции **пересчитывать только строки договора и договорный итог**; не вызывать новый тарифный расчёт.
3. Если договорный итог отличается от первоначальной стоимости, показывать **«Цена договора отличается от согласованного заказа: X ₽ → Y ₽ (разница Z ₽)»**.
4. Перед PDF требуется отдельное подтверждение расхождения с обязательным комментарием. По умолчанию исходный заказ остаётся без изменений.
5. Отдельное действие «Создать новую согласованную версию заказа» — только во втором этапе, без тихого перезаписывания предыдущей версии.

## 6. Экранный сценарий
`Сохранённые заказы → [Договор] → редактирование → предпросмотр → PDF/печать`.
Редактор с вкладками/секциями: **Клиент и объект**, **Работы и стоимость**, **Время/условия**, **Документ/реквизиты**. На мобильном одна колонка, фиксированная заметная кнопка «Предпросмотр», числовые поля с правильной клавиатурой. Просмотр: реальные страницы A4 и их количество, фирменная шапка исключительно на первой странице каждого самостоятельного документа, пустой нижний колонтитул, таблица допуслуг, подписи в конце, понятные разрывы. Возврат к редактированию без потери правок.
Сохранение черновика должно происходить при изменении и при закрытии редактора; показывать видимое состояние «Сохранено» / «Ошибка сохранения». При первой генерации договор нельзя считать заключённым или подписанным.

## 8. PDF и лицензии
Текущий `html2pdf` делает смету как **одну длинную страницу**. Для договора лучше отдельный A4-модуль, использующий существующие html2pdf/html2canvas/jsPDF лишь после подтверждения стабильности на 1/3/8 страницах; при неудовлетворительных разрывах — оценить самостоятельную пагинацию A4, не ломая смету. Использовать локальный Orbitron только там, где нужно; русские буквы лучше оставлять в подходящем локальном текстовом шрифте. Проверить лицензию каждой библиотеки до добавления.

## 9. Совместимость и защита данных
- `contractDrafts` — отдельная коллекция, не мутировать старые `savedOrders`.
- Добавить `schemaVersion`, миграции старых заказов; без исторического списка работ показывать предупреждение, не создавать «задним числом» якобы исходный список.
- Изоляция черновиков по `orderId`; backup должен включать их только при явном выборе/новой версии формата.
- HTML-шаблоны экранируют произвольный ввод; нельзя вставлять пользовательский HTML через `innerHTML` без очистки. Содержимое личных данных не отправлять в внешние сервисы без явного действия.
- Проверять конечность сумм, корректность телефонов/дат и длину текста; запрещать генерацию пустого или несовместимого документа.

## 10. Готовность MVP
Выполнены сценарии из `TEST_PLAN.md`: импорт старого заказа, одна услуга, несколько допуслуг, ручная правка ФИО/телефона/времени, изменение стоимости с предупреждением, повторное открытие черновика, PDF 1–8 страниц, смартфон/кириллица. Исходные расчёт и сохранённая цена не меняются без отдельного действия.

## 11. Согласованные решения — 14.10.2026

| № | Вопрос | Согласованное решение | Техническое следствие |
|---|---|---|---|
| 1 | Исполнитель | **ИП** | Раздел данных исполнителя: полное наименование ИП, ИНН, ОГРНИП, реквизиты, контакты. Конкретные значения не выдумывать. |
| 2 | Юридическая база | **Есть действующий договор** | Использовать только исходный действующий документ; хранить утверждённую редакцию как versioned template, не создавать «новый юридический договор» вместо него. |
| 3 | Заказчики | **Физические и юридические лица** | Поле `customerType = individual | legal_entity`; разные наборы реквизитов, режимы договора; юрлица не реализовывать по неподтверждённому тексту. |
| 4 | Цена вручную | **Разрешать с отдельным подтверждением и причиной** | При расхождении `contractTotal != quoteSnapshotTotal` блокировать экспорт до подтверждения и непустой причины; сохранять исходную цену, изменённую цену, причину, дату и пользователя (если идентифицирован). |
| 5 | Время начала | **Вводить в калькуляторе** | Добавить `form.cleanStartTime` как время HH:MM; переносить в `savedOrder.form`, `quoteSnapshot.schedule` и договор, поддержать старые заказы без этого поля. |

### 11.1. Рекомендованная конкретизация решений
- Для B2C: ФИО, телефон; дополнительные паспортные/адресные поля **только если они реально нужны утверждённому шаблону**.
- Для B2B: название организации, ИНН, КПП (если предусмотрен), представитель и основание полномочий, банковские реквизиты — только по полям действующего договора; не смешивать с личными контактами.
- Юридические реквизиты ИП отделить от публичного рекламного названия PRO-CHISTKA. В публичный `config.js` не помещать клиентские персональные данные, подписи, чувствительные вложения.
- Дата уборки уже есть в `form.cleanDate`; время начала добавить рядом. Время окончания вычислять лишь как ориентировочное при наличии корректных нормо-часов/бригады, редактировать вручную и не выдавать расчётную оценку за договорённое время.
- При ручном изменении цены калькулятор **не изменяет исходный заказ**. В редакторе показывать «Цена заказа / Цена договора / Разница» и требовать отдельное подтверждение + комментарий. Во внешний PDF попадает актуальная подтверждённая цена договора; внутренняя причина хранится в черновике/истории.
- Номер договора и дата договора — отдельные поля с редактированием; автонумерация не должна порождать дубликаты при работе с несколькими устройствами. Для MVP допустимо формировать предложение номера и требовать проверку уникальности менеджером.

### 11.3. УТВЕРЖДЕНО: фирменный колонтитул только на первой странице каждого самостоятельного документа

**Подтверждено:** верхняя фирменная шапка **только на первой странице исходного документа**, а не на каждой. Она выполнена таблицей из двух колонок без встроенных картинок: слева `PRO-CHISTKA` шрифтом **Orbitron Black 24 pt** и подпись «клининговые услуги» (12 pt), справа контакты **Arial 10 pt bold**, справа выровнены; под шапкой — тонкая линия. Следующие страницы без шапки, нижний колонтитул пуст, номера страниц нет. Страница A4, поля по 1,27 см сверху и снизу.

**Окончательное решение владельца (14.10.2026):** единый компонент `DocumentBrandHeader` обязателен для каждого **самостоятельного документа** — договора B2C, договора B2B, сметы/КП, акта и приложения — **исключительно на его первой странице**. На второй и последующих страницах данного документа фирменная шапка отсутствует. При сборке пакета самостоятельных документов (например, договор + акт) каждый документ начинается с новой секции/страницы и получает собственную шапку только на своей первой странице. Никакого повторения на всех страницах, дополнительного нижнего колонтитула или автоматической нумерации страниц не добавлять: в исходниках нижний колонтитул пустой, нумерации нет. Решение утверждено, дополнительного вопроса о режиме шапки больше нет.

**Технически:** единый `DocumentLayout` обязательно содержит `headerMode:'first-page'`, `header`, `footerMode:'empty'`, `pageNumbers:false`, `templateVersion`, `documentType`, настройки A4 и шрифта. Нельзя сбрасывать/заменять существующие `state.pdfHeader` и сметный PDF без визуального сравнения. Локальный Orbitron использовать начертанием 900 в фирменной шапке. Перед PDF дождаться загрузки шрифтов.

**Приёмка:** сравнить фирменную шапку первой страницы с оригиналом; на 2-й и последующих страницах каждого документа верхний колонтитул отсутствует, нижний остаётся пустым. Общий шаблон (4 страницы) и два B2B-образца (по 3 страницы) служат эталонами внешнего вида. Проверить отдельно сформированные договор, смету, акт, приложение и пакет «договор + акт»; у акта шапка только на первой странице самого акта. PDF/печать на 1/3/8 страниц не должны обрезать или перекрывать содержимое.

### 11.3.1. Юридический текст не подменять автоматически

Структура исходников содержит предмет, права/обязанности, оплату и приёмку, ответственность, реквизиты сторон и акт. B2B-примеры имеют конкретные перечни работ и расширенную налоговую формулировку, которой нет в таком виде в общем шаблоне. В частности, ссылку на пункт 1 статьи 145 НК РФ и описание отсутствия НДС нужно отдельно согласовать с бухгалтером/юристом с учётом актуального режима ИП. **Не считать наличие фразы в образце проверкой её законности и актуальности.** Любую ручную правку договора хранить отдельно от сохранённой цены заказа.

### 11.4. Граница текущего согласования
Пять ответов фиксируют **поведение будущей функции**, но не дают разрешения на изменение `production`, запуск реальных публикаций Apps Script, изменение тарифов или финализацию юридического текста. Ближайший этап разработки — A, стабилизация безопасного основания, см. `STAGE_A_PLAN.md`.
