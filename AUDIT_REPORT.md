# AUDIT_REPORT.md — PRO-CHISTKA Calculator

Дата аудита: 14.10.2026. Исходный production commit: `93b589b4837e0577ff13213186205bdcbbda93c4`. Версия приложения: **v4.11.24**, конфигурация: **ревизия 24**.
Статус: аудит исходников и локальные безопасные тесты; **ни один пользовательский заказ и ни одна настройка production не изменены**. Все новые документы находятся только в ветке `audit-2026-10-14`.

## 1. Краткий вывод
Проект — рабочий автономный веб-калькулятор с хорошим разделением чистого расчётного ядра, редактора настроек, рендера сметы и хранения. Текущий механизм достаточен для смет и небольшого числа локальных заказов. Основные слабые места перед развитием: **проверка входных чисел, модель исторического заказа, устойчивость хранения, качество регрессионных тестов и подтверждение синхронизации**. Генератор договора можно встроить **без переписывания калькулятора**, если использовать один неизменяемый снимок согласованной цены.

## 2. Фактическая архитектура
- `index.html`: HTML-формы, настройки, тарифы, экран заказов и PDF-модальные окна; `assets/style.css`: адаптивная вёрстка.
- `config.js`: глобальные тарифы, категории, виды уборки, описания, настройки PDF и опубликованная ревизия (не содержит безопасного серверного хранилища).
- `assets/core.js`: независимые от DOM `calculateOrder`, `validateOrder`, `validateBackup`; начисление базовой цены, коэффициентов, минимального заказа, допуслуг, выезда, скидки, труда, материалов, накладных и налогов.
- `assets/js/state.js`: локальная модель, миграции, localStorage + IndexedDB, принятие ревизий, конфликтная логика.
- `assets/js/helpers.js`: подготовка конфига, запросы к GitHub raw/API, публикация через iframe POST в Apps Script, тексты синхронизации.
- `assets/js/settings.js`: интерфейс тарифов, редактор услуг и настройки.
- `assets/js/estimate.js`: отображение расчётов, список заказов, повтор заказа, текст и HTML сметы, PDF через html2pdf/html2canvas/jsPDF.
- `assets/js/main.js`: обработчики UI, сохранение заказа и инициализация.
- `sw.js`: service worker, стратегия network-first, запасной кэш приложения; `assets/fonts/Orbitron-Variable.ttf`: локальный Orbitron.
- `integrations/google-apps-script/Code.gs`: проверка секрета, контроль ревизии, GitHub Contents API PUT; реальные Script Properties/deployment без отдельного доступа не проверены.
- `tests/core.test.js` и `tests/e2e.js`: Node и Playwright тесты.

### Поток данных
`Форма и допуслуги → state → CORE.calculateOrder(state) → результат расчёта → recalc()/смета → savedOrders (локально) → buildPrintHtml()/generatePdfBlob()`.
Синхронизация: `локальные настройки → buildConfigPayload() → Apps Script POST → GitHub production/config.js → проверка GitHub → применение конфигурации на устройствах`.
Для договоров необходим новый поток: `savedOrder + frozenQuoteSnapshot → ContractDraft (отдельные правки) → договор/приложение/превью → PDF`.

## 3. Фактические тесты
Проверялась отдельная копия `production` на подключённом ПК с Node.js v24 и установленным Google Chrome через Playwright. Исполняемый e2e-тест локально был направлен на установленный Chrome; файл в GitHub не менялся.
- **Node unit: 9/9 успешно** (минимальные цены, выезд, труд, сведение сумм, отдельно доступные допуслуги).
- **Playwright E2E: неполный / красный.** Были успешны загрузка локального Orbitron, создание PDF, загрузка/повтор/удаление заказа, синхронизационные UI-утилиты, основные строки сметы. Не прошли проверка равенства снимка для собственной публикации, три ожидания старой схемы «серии», ожидание автоматического увеличения рекомендованной цены. Затем тест завершился таймаутом, поскольку `#forceDiscount` отсутствует. Не выдавать эти 5 FAIL за 5 дефектов расчёта: часть тестов устарела относительно приложения.
- **Lint: не проходит**. ESLint: `assets/js/helpers.js:185` — `preserve-caught-error`; `assets/js/helpers.js:389` — `no-useless-assignment`. CSS/HTML этапы не были запущены, так как цепочка остановилась на JS.
- **Отдельный browser-smoke**: проверка viewport 320/375/390/430/768/1280 px; `scrollWidth>innerWidth` при 320 (323px) и 430 (482px). Требуется уточнить источник сдвига визуальным исследованием, так как по простым DOM-bounding-box фильтрам видимый виновник не выделился. При остальных размерах нет общего переполнения.
- **Мобильный PDF**: браузер при 390px сформировал Blob `application/pdf`, заголовок `%PDF-`, размер ~907КБ; это **не** доказывает корректность каждого переноса или всех шрифтов в документе.
- **Историческая цена**: зафиксированная в записи сумма 17 010 ₽ сохранилась. После повышения ставки и команды «Повторить» новая цена стала 23 814 ₽. Следовательно, «Повторить» — новый расчёт, не просмотр неизменённой сметы.
- **Граничные условия**: -20/0 м² отклоняются; 0.1 и 1 м² получают минимальный тариф 12 000 ₽; при площади 1e308 результат не конечен, а в JSON представляется null, `validateOrder` такой ввод не блокирует. 100% скидка доводит цену до 0 — бизнес-ограничение требует согласования. `validateBackup` принимает структурно похожий объект с некорректными полями `form`.

## 4. Выводы по направлениям
### Расчёты
Базовые сценарии реализованы и unit-тестируются. Для сверхбольших чисел и политик скидок не хватает серверонезависимых ограничений. Конфигурационные тарифы не менять без согласования; для будущих документов предусмотреть `quoteSnapshot` и независимый расчёт итогов позиций договора только из уже утверждённого снимка.
### Сохранность
Данные заказа и черновики хранятся **на конкретном устройстве**; IndexedDB дублирует полное состояние, но находится в хранилище того же браузерного профиля. Очистка данных браузера/переход на другое устройство не гарантирует восстановление. Функция `saveState` перехватывает сбои записи без уведомления пользователя. Для договора нужен отдельный объект `contractDrafts` с версией схемы и возможностью резервирования.
### Безопасность
`config.js` публичный, `APP_PASSWORD` — не серверная авторизация (на проверенной ревизии значение пустое). Настоящий секрет публикации предназначен для Script Properties Apps Script; при клиентском XSS он потенциально доступен из страницы/сессионного хранилища. Интерполяции пользовательских полей в HTML в ключевых местах экранируются через `esc`, но каждый новый шаблон договора должен соблюдать такую же дисциплину.
### Синхронизация
Apps Script использует проверку `SYNC_SECRET` и оптимистическую блокировку SHA GitHub; есть блокировка скрипта. Однако зеркало `GITHUB_PAGES_BRANCH` по умолчанию направлено в устаревшую ветку и может дать ответ с ошибкой **после успешной записи production**. Клиентская проверка `revision>=expected` не сверяет контент/хэш публикации. Подлинный POST и конфигурацию активного Apps Script не тестировали во избежание изменения рабочих тарифов.
### UX/PDF
Есть подробная редактура услуг, превью PDF и мобильный режим; документ формируется как **одна длинная PDF-страница**, а не реальная многостраничная пагинация. Для договора это недостаточно. Превью редактируемого договора должно наглядно показывать источник полей и расхождения цены.

## 5. Общая оценка
Для ежедневных расчётов: **условно пригоден**, но нужна стабилизация данных и тестов. Для генерации юридических документов: **архитектурно пригоден после добавления модели исторической цены, шаблона и черновиков**. Массовая переработка ядра не требуется. Главный порядок: границы ввода и сохранность → актуализация тестов → модель заказа/контракта → UI и PDF.
