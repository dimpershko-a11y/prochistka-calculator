## 0. Согласованные принципы генератора договора
1. Исполнитель — **ИП**; реквизиты и юридическое наименование берём из действующего документа, не придумываем.
2. Есть **общий шаблон** и **пример договора с юрлицом**; нужен доступ к обоим файлам для точной схемы и юридических условий. B2C + B2B должны использовать общий дизайн/структуру с различиями реквизитов и утверждённого текста.
3. Разница стоимости заказа и договора допускается **только с подтверждением и обязательной причиной**; исходная цена не меняется.
4. Время начала уборки — новое поле `cleanStartTime` непосредственно в калькуляторе (формат HH:MM, опциональное для исторических записей).
5. **Верхние и нижние колонтитулы обязательны для ВСЕХ документов:** договор физлица, договор юрлица, смета/КП, приложения, будущий акт, печать и PDF. Сохранить оригинальное оформление и повторение на страницах. Текущие колонтитулы/шапку сметы не сломать. Различия в оформлении определить по образцам; пока образцы не доступны, не рисовать альтернативу.

## 1. Цель первого этапа
Стабилизировать калькулятор без изменения тарифов и существующих алгоритмов коммерческого расчёта. Подготовить неизменяемый снимок согласованной суммы (`quoteSnapshot`) и контролируемую модель времени начала, чтобы затем строить договор на достоверных данных.

Первый этап **не включает** выпуск генератора договора, изменение текста действующего договора, массовую переделку интерфейса или публикацию в production.

## 3. Принципы реализации
- **Чистый расчёт** остаётся в `CORE.calculateOrder`. Внесение нового бизнес-правила по скидкам и минимуму запрещено без отдельного решения. 100% скидка сегодня может давать 0 ₽ — это отдельный вопрос политики, не исправлять молча.
- Валидация и проверка сохранения — в одном месте, сообщение пользователю при отказе.
- Исторический `quoteSnapshot` — неизменяемый объект для документов; новый расчёт по действующим тарифам — отдельное действие.
- `cleanStartTime` не вносить в `config.js` как персональное значение; допустим только пустой дефолт поля. Записи старого формата остаются читаемыми.
- Разработка только в отдельной ветке. Изменения Apps Script в GitHub **не** обновляют опубликованный Google deployment; его настройки/релиз отдельно после разрешения.
- **Общие колонтитулы документов** закреплены как отдельное требование уже на этапе A; сам HTML/PDF шаблон будет интегрироваться на этапе D после предоставления образцов.

## 4. Риски и защита
- Хранилище в браузере: перед любыми тестами миграции — копия реальных данных или синтетическое тестовое состояние; тесты не проводят сброс пользовательского localStorage.
- Apps Script: никакого реального PUT и повышения CONFIG_REVISION в ходе первого этапа без разрешения; использовать мок или тестовый репозиторий/Script deployment.
- Схема заказа: резервировать старые форматы; новый `quoteSnapshot` записывать для новых заказов, а для старых только после подтверждённого восстановления недостающих данных.
- Мобильная версия: проверить и визуально найти горизонтальное переполнение при 320/430px, не обрезать интерфейс костылём `overflow-x:hidden`.
- Колонтитулы: не обещать тождественность оригиналу до сравнения файлов; сохранять текущую PDF-шапку до перехода.

## 5. Критерии приёмки и границы разрешения
Первый этап готов только когда автоматические тесты чистые, сохранность старых заказов доказана, существующие рабочие цены не изменились для валидных данных, время и снимок заказа покрыты тестами, и подготовлен diff для проверки владельцем.

**Одобрение ПЛАНА не означает одобрения записи в production.** Перевод релиза и обновление реального Apps Script — отдельное согласование. Режим по умолчанию: dev-ветка, отчёт и тесты.
